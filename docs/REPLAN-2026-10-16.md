L1 **code and radius rules** (first-order bounds are `Mag` arithmetic, `PLAN:344-349`; domain logic; exact-touch endpoint evaluation) do not need the pin and can be written against an mpmath-supplied midpoint or a stub; what stays red until B is the green gate on real zf kernels. I could not determine how many L1 call sites change when Option A lands (that is Rusty's knowledge).
- **L2a-c** (complex, poly, series, matrices): L2b/L2c need only L0b (see 3b). L2a complex exp/log/sqrt need L1 (exp, ln, atan2, pi), so they inherit Stage B. Complex Rect/Disk arithmetic needs only L0b.
- **L2d specials** (gamma, erf, J0/J1, zeta, and the rest): need L1 constants and exp/ln; those using "zf's correctly rounded value at the midpoint plus a proven bound" (`PLAN:362`) trust zf specials, which are **outside the P14 scope** ("exactly the kernels listed", `PLAN:195`). I could not determine whether any audit of zf specials is planned; if none, L2d needs either certified series in zenith-bound (more effort) or a new zf audit item.
- **L3 quadrature**: needs L1 and L2a (ball functions on complex balls, Bernstein-ellipse bound). After L1/L2a.
- **L4**: adaptive precision, root isolation, verified solve (needs L2c), residuals, eigen, ODE (needs ball AD and L1). The shell and the L2c-based solve can be built before B; evaluation of real expressions (`N[expr, d]` is item 1 of the Accumath order, `PLAN` Part F) needs L1.

## 6. What reduces the risk (decisions are Jeff's unless marked)

1. **Start Stage-A-free L0b parts and red tests now** (3a). Cost: some rework if Stage A changes P2/P3 shapes. Needs Paul's/Jeff's OK because it goes beyond "L0b may start after Stage A".
2. **Build L1-L4 code against a stub backend** (a trait over the handful of zf operations, mids supplied by mpmath in tests): radius rules, domain logic, exact-touch endpoint evaluation, `Tri`, L2b/L2c, L4 shell need no pin. Limits: it cannot test P14, constants, or real kernel rounding; the green gate still waits for Stage B. Design owner: Rusty/Paul (CONTRACT 15.1 fixes the by-value/borrowed shapes).
3. **Parallel lanes** (A6): moves done dates 18 days earlier (likely estimate) to 37 days earlier (pessimistic estimate) in the tables above [D]. Needs review capacity (A7).
4. **Split Stage B**: freeze signatures (and ship P14/P11) for **only the functions L1 v1 calls** first, and defer the rest of Option A. This is the lever with the biggest effect on the pessimistic case. Owner: Rusty/Paul.
5. **P14 alternative** (`PLAN:195`): `ToEven` plus a proven ≤ 1 ulp bound, or certified kernels in zenith-bound (the "main L1 cost driver", PLAN Part H), removes L1's dependence on the Ziv audit but adds L1 effort. Rusty decides per kernel.
6. **Scope cuts Jeff must decide.** `PLAN:10` says "Scope L0-L4 before the Accumath launch"; Part F orders Accumath's use: (1) `N[expr, d]` and precision display, (2) special functions, (3) roots, (4) LA solve and determinant, (5) quadrature, (6) ODE ("last; opt-in"). I found no document that says which layers Accumath **v1** actually needs, and no Accumath file references zenith-bound (grep of the Accumath tree, excluding `target`, found none). Candidates, with their Part G sizes: ODE (Lohner, 10-20 runs, already "opt-in"), L3 quadrature (10-20), L2d beyond gamma/lgamma/erf/J0/J1/zeta (Meijer/Fox/Heun already "refuse" in v1), eigen-enclosures, L4 root isolation. TEST_PLAN 19 already offers a "floor" test scope for L2-L4 (saves 25-35% of their test gross). A cut must be recorded in the level's exit commit, not silently.
7. **Move the ship date or the dependency**: Accumath pins zenith-float `=1.0.12` today (`option-a-evidence.md:19`), and zenith-bound could ship against a release that is not Stage B if L1 used the P14 alternative; that is a Jeff/Rusty decision.
